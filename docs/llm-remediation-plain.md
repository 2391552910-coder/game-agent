# LLM 侧问题白话说明

## 一句话结论

MyAgent 需要完整接入 Gateway v2 的 21 种技能合同。当前主要问题是事件格式仍有差异、技能最终结果可能被新一轮状态覆盖，以及暂时没有新动作时会把正常事件误报成错误。

## 1. 先把双方说话格式完全对齐

Gateway 发来的事件有固定外壳、租约、技能说明和参数提示。MyAgent 必须按这些真实字段接收，不能继续使用自己手写的旧格式。否则新增字段会被当成非法，真正需要的字段又会被误报缺失。技能结束只有成功、失败、取消、超时四种；“决策被拒绝”是另一类事件，不能混进技能结束状态。

这个问题已经能稳定复现：签名正确时，MyAgent 仍会因为事件字段形状不认识而返回 `400`。不是网络断开，也不是密钥错误；密钥错误应当返回 `401`。要改的是 MyAgent 接收事件的数据模型，不能让 Gateway 删除正确字段来迁就旧模型。

## 2. 要把“这是哪一个父动作”交给决策层

停止移动要知道正在停止的是 `move_to`，退出热气球或直升机也要知道当前窗口属于哪个载具。这个信息 Gateway 已经放在 lease 里，MyAgent 需要原样交给 Agent，不能再猜。

## 3. 新一轮对话不能冲掉上一件事的最终结果

现在出现过这些情况：退出载具在 Gateway 已经成功，MyAgent 还一直显示 `started`；停止移动成功后，父移动也没有结束。需要按每次技能自己的 `skillCallId` 保存最终结果，即使 session 已经进入下一轮，也要把旧技能的成功、失败或取消正确落库。

根因是新一轮开始后，MyAgent 会把上一轮的所有消息直接当作过期消息丢掉，其中包括“技能已经结束”的消息，所以旧技能没有机会更新最终结果。修复时只允许旧技能的开始、结束和决策被拒绝事件回填原记录；旧的状态更新和旧的停止托管事件仍不能干扰新一轮，也不能触发新的 Agent 决策。

## 4. 暂时没有动作不等于接口坏了

Agent 还在思考、没有计划或计划已经用完时，事件入口不应该返回 400，能力接口也不应该变成 503。正确做法是先可靠收下事件，再异步决定动作；暂时不做事就返回合法的等待，而不是把 Gateway 推入重试风暴。

## 5. 测试数据必须来自 Gateway 真正发出的事件

六种非聊天事件都要有从 Gateway 合同导出的样例。以后 Gateway 改字段，MyAgent 的 CI 应该马上发现，而不是等到真实环境才出现 400。

## 6. 两个方向继续使用两套钥匙

Gateway 发事件给 MyAgent，和 MyAgent 回调 Gateway，是两个信任方向。两套身份不能混用，错误组合必须被拒绝，日志里不能出现钥匙内容。

## 7. 启动配置也要跟上 v2

MyAgent 现在除了钥匙，还要明确写清楚“哪一个 Gateway 可以用这个 AppId”和“这个 Gateway 属于哪一个 UUID 租户”。旧配置缺少前一个映射，并把本地 Gateway 配到了一个普通名字，不是 UUID，所以 v2 会拒绝启动。

数据库也必须升级到 v2 的最新结构；Rerank 如果被打开但服务不可用，MyAgent 会为了安全拒绝提供 capabilities。正确做法是补齐真实服务，或者在不提供 Rerank 的部署环境中明确关闭这个可选依赖，不能让 Gateway 对着 `503` 一直重试。

## 处理顺序

先修事件格式和终态收敛，再补父动作上下文和异步 ACK，最后补合同 fixture 与完整非聊天回归。聊天功能保持不接入。
