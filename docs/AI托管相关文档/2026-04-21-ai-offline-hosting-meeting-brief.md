# AI 离线托管会议讨论稿

## 文档定位
本文档用于和策划、实现同事开会讨论 **AI 离线托管** 方向。

这是一份 **讨论稿 / 对齐稿**，不是实现说明，也不是当前 Unity 客户端工程的开发任务单。

本文档只整理思路、边界、版本目标、风险和待拍板问题，不绑定具体实现语言、框架或仓库结构。

## 一句话结论
建议把这个能力做成一个 **独立的 AI 托管中转层项目**：

- 大模型只负责“决策下一步做什么”。
- 中转层负责“登录、状态、校验、限频、审计、协议发送”。
- 当前客户端工程只作为 **只读参考源**，不承载这套系统。

## 为什么现在要讨论这件事
我们要实现的不是传统游戏行为树机器人，而是 **真实大模型驱动的角色托管**。

这个方向如果直接让大模型模拟客户端裸发协议，短期可能快，但中长期会遇到这些问题：

- 大模型可能幻觉参数，导致乱发协议。
- 协议和客户端实现强耦合，后续维护成本高。
- 很难做权限控制、限频、熔断和审计。
- 很容易把“讨论方案”误做成“客户端改造任务”。

所以在动手前，需要先把产品目标、版本边界和实现边界说清楚。

## 当前建议方案
### 方案核心
把系统拆成三层：

1. **Decision Provider**
   负责决定下一步行为。
   可以是大模型，也可以先是规则脚本、测试回放器或人工调试器。

2. **Hosting Gateway**
   负责托管会话、登录、状态管理、skill 执行、权限校验、限频、审计和熔断。

3. **Protocol Contract + Adapter**
   负责把中转层允许的 skill 映射到游戏服已有协议。

### 最重要的设计句子
**大模型只负责决策，中转层负责执行约束。**

## 必须先讲清楚的边界
### 1. 这不是客户端内嵌功能
- AI 调度、中转层、skill 执行器、会话池、并发调度都应放在独立项目。
- 当前 Unity 客户端工程不负责运行这套系统。
- 当前客户端只提供协议、接口用法和行为语义的只读参考。

### 2. 不修改当前客户端
- 不为了这套能力去改当前客户端代码。
- 不要求在 `Assets/Scripts/Codes` 下新增 AI 托管运行时代码。
- 如果后续发现协议能力不够，应先提需求和方案，不直接改客户端。

### 3. 不绑定当前技术栈
- 后续实现可以用 Python，也可以用其他服务端技术栈。
- 方案不要求继续使用 Unity、ET、C# 或当前仓库结构。
- 当前客户端技术点只能作为“参考案例”，不能作为实现约束。

### 4. 不让大模型直接拼协议
- 大模型不应直接接触裸协议字段。
- 大模型只调用受控 skill。
- skill 通过中转层再转成真实协议。

## 为什么推荐中转层，而不是让大模型直接发协议
### 推荐原因
- 更容易做权限控制。
- 更容易做参数校验和状态校验。
- 更容易做限频、熔断和审计。
- 更容易支持多种决策源，不被某个模型或某种实现绑死。
- 更容易逐步扩展能力，而不是每加一个行为就改一遍底层。

### 不推荐直接裸发协议的原因
- 大模型有幻觉风险。
- 协议升级后容易失配。
- 错误定位困难。
- 并发账号下更容易失控。

## 版本目标
### v0.1
目标是先证明 **单账号基础闭环**。

建议范围：
- 托管授权。
- 登录。
- 进入指定场景。
- 观察当前状态。
- 移动。
- 跑。
- 停止移动。
- 跳。
- 基础动作白名单。
- 审计日志。

建议成功标准：
- AI 能登录并进入指定场景。
- AI 能稳定完成移动、跑、跳、基础动作闭环。
- 非法动作不会发出真实协议。
- 全过程有审计链路。

### v1.0
目标是证明 **多账号稳定托管**。

建议范围：
- 多账号并发登录。
- 每账号独立会话。
- 心跳和重连。
- 并发行为循环。
- 单账号异常隔离。
- 乱发协议防护。
- 熔断和恢复。
- 审计回放。

建议成功标准：
- 多个账号可并发运行指定时长。
- 不出现系统性掉线。
- 不出现明显乱发协议。
- 单账号异常不会拖垮其他账号。

## 当前明确不做的内容
`v0.1` 和 `v1.0` 建议先排除高复杂度行为：

- 聊天和自由文本社交。
- 任务、活动、收益领取。
- 背包、交易、付费、抽奖。
- 战斗、竞技、排行榜。
- 大模型直接拼裸协议。
- 当前客户端改造。

这样做的目的不是永远不做，而是先把底座跑通，再逐步扩能力。

## 讨论时建议统一的理解
### 1. “像客户端一样接管行为”是什么意思
这里建议把成功标准定义成：

**以服务器可观测状态变化为准。**

也就是说：
- 角色是否真的登录成功。
- 是否真的进入指定场景。
- 位置是否真的变化。
- 跳跃和动作是否真的被服务器接受。

不要求第一阶段复刻 Unity 客户端本地动画、路径插值或表现层细节。

### 2. “大模型驱动”不等于“第一天就必须接大模型”
为了降低风险，建议保留一个更稳妥的推进方式：

- 先用规则脚本或测试回放器接入同一套 skill 边界。
- 先把网关、协议、会话、审计、熔断跑通。
- 再把真实大模型挂到同一决策接口后面。

这不会偏离目标，反而更利于快速验证底座。

## 建议会议重点讨论的问题
### 面向策划
- 这个能力第一阶段的业务目标是什么。
- `v0.1` 指定场景选哪个。
- `v0.1` 基础动作白名单包含哪些动作。
- `v1.0` 想验证的“并发量”和“运行时长”大概是多少。
- 后续优先扩展的是社交能力，还是轻互动能力。

### 面向实现同事
- 独立项目准备放在哪个仓库。
- 是否优先用 Python 实现。
- 中转层怎么和游戏服通信。
- 协议 source of truth 是什么。
- 独立项目消费什么协议产物。
- 如何做协议一致性校验。
- 如何做 traceId、sessionId、skillCallId 的统一追踪。

### 需要双方一起拍板
- 托管授权方式是否使用专用 token。
- 是否允许先用脚本决策器验证 v0.1。
- v0.1 的成功指标怎么定义。
- v1.0 的并发和稳定性指标怎么定义。

## 会议建议输出
这次会建议至少输出以下结论：

1. 是否确认采用 **独立项目 + 中转层 + skill + 协议适配** 方向。
2. 是否确认 **不修改当前客户端**。
3. 是否确认 **技术栈中立**，允许 Python 等实现。
4. 是否确认 `v0.1 / v1.0` 的版本边界。
5. 是否确认第一阶段排除高复杂度行为。
6. 是否确认协议 owner、同步 owner、验收 owner。
7. 是否确认 `v0.1` 的指定场景、动作白名单和测试账号。

## 建议的下一步
如果会议达成一致，建议后续输出两类东西：

- 一份更正式的 **实现前方案文档**。
- 一份更具体的 **v0.1 / v1.0 验收表**。

这两份文档都应继续保持技术栈中立，并明确“这是独立项目方案，不是 Unity 客户端改造任务”。
