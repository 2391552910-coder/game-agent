# myAgent 与 RobotGateway 通信文档

本文档说明 myAgent 与 RobotGateway 的 HTTP 对接方式，供 myAgent 开发方、RobotGateway 开发方、联调人员和运维人员共同参考。

当前项目实现以 HTTP 为主通信方式：

```text
RobotGateway --HTTP Webhook--> myAgent
myAgent --HTTP Snapshot Pull--> RobotGateway
myAgent --HTTP Callback--> RobotGateway
```

## 1. 系统角色边界

### 1.1 RobotGateway 职责

RobotGateway 负责游戏账号和游戏进程侧的运行控制，主要职责包括：

- 管理玩家账号、会话、在线状态和运行节奏。
- 整理玩家当前快照 `snapshot`。
- 在玩家状态变化时向 myAgent 发送事件。
- 在 myAgent 未收到快照时，提供玩家快照查询接口。
- 接收 myAgent 分析完成后的回调结果。
- 根据回调结果自行决定是否进入动作校验、动作执行或人工审核流程。

RobotGateway 不应依赖轮询 myAgent 的分析查询接口作为主链路。主链路应以 myAgent 主动 callback 为准。

### 1.2 myAgent 职责

myAgent 负责 AI 分析与决策建议，主要职责包括：

- 接收 RobotGateway 推送的玩家事件。
- 对离线事件做 Redis 去重，避免重复提交分析。
- 通过 Prefect 提交并执行离线分析流程。
- 在缺少快照时主动向 RobotGateway 拉取玩家快照。
- 调用 LangGraph Agent、RAG、LLM 和数据库能力生成分析结果。
- 将分析结果写入 PostgreSQL。
- 在结果持久化成功后，通过 HTTP callback 推送给 RobotGateway。

myAgent 不负责游戏账号登录、动作安全校验、游戏内动作最终执行。

## 2. 通信总览

### 2.1 三条 HTTP 通信链路

| 方向 | 发起方 | 接收方 | 用途 | 当前代码入口 |
|---|---|---|---|---|
| RobotGateway -> myAgent | RobotGateway | myAgent FastAPI | 推送玩家事件 | `src/api/routes/webhooks.py` |
| myAgent -> RobotGateway | myAgent Prefect Flow | RobotGateway | 拉取玩家快照 | `src/game_specific/connector.py` |
| myAgent -> RobotGateway | myAgent Prefect Flow | RobotGateway | 推送分析完成结果 | `src/core/integration/robotgateway_callback.py` |

### 2.2 主流程

```text
1. RobotGateway 判断玩家进入需要分析的状态
2. RobotGateway POST /webhooks/player-event 到 myAgent
3. myAgent 根据 X-API-Key 识别 tenant_id
4. myAgent 对 offline 事件执行 Redis 去重
5. myAgent 提交 Prefect Deployment: analysis_flow/offline-analysis
6. Prefect Flow 获取 snapshot
   6.1 如果 Webhook 已带 snapshot，直接使用
   6.2 如果 Webhook 未带 snapshot，向 RobotGateway GET /players/{user_id}/snapshot
7. myAgent 运行 LangGraph Agent
8. myAgent 写入 analysis_results
9. myAgent POST callback 到 RobotGateway
10. RobotGateway 接收 analysis.completed，进入后续处理
```

## 3. 环境变量配置

### 3.1 myAgent 侧配置

myAgent 需要配置以下与 RobotGateway 通信相关的环境变量：

```env
GAME_DATA_SOURCE=robotgateway
ROBOTGATEWAY_BASE_URL=http://127.0.0.1:9000
ROBOTGATEWAY_SNAPSHOT_API_KEY=
ROBOTGATEWAY_SNAPSHOT_TIMEOUT_SECONDS=10

ROBOTGATEWAY_CALLBACK_URL=http://127.0.0.1:9000/callbacks/analysis
ROBOTGATEWAY_CALLBACK_API_KEY=
ROBOTGATEWAY_CALLBACK_TIMEOUT_SECONDS=10
```

字段说明：

| 配置项 | 必填 | 说明 |
|---|---:|---|
| `GAME_DATA_SOURCE` | 建议 | 设置为 `robotgateway` 时，myAgent 通过 HTTP 向 RobotGateway 拉取快照 |
| `ROBOTGATEWAY_BASE_URL` | 条件必填 | RobotGateway 基础地址，例如 `http://127.0.0.1:9000` |
| `ROBOTGATEWAY_SNAPSHOT_API_KEY` | 可选 | myAgent 拉取快照时发送到 RobotGateway 的 `X-API-Key` |
| `ROBOTGATEWAY_SNAPSHOT_TIMEOUT_SECONDS` | 可选 | 拉取快照超时时间，默认 10 秒 |
| `ROBOTGATEWAY_CALLBACK_URL` | 条件必填 | myAgent 分析完成后回调 RobotGateway 的完整 URL |
| `ROBOTGATEWAY_CALLBACK_API_KEY` | 可选 | myAgent 回调 RobotGateway 时发送的 `X-Callback-API-Key` |
| `ROBOTGATEWAY_CALLBACK_TIMEOUT_SECONDS` | 可选 | 回调超时时间，默认 10 秒 |

如果 `ROBOTGATEWAY_CALLBACK_URL` 未配置，myAgent 会跳过 callback，不会让分析流程失败。

### 3.2 本地脚本配置

当前仓库已有 HTTP 联调启动脚本：

```bat
scripts/run_api_robotgateway.cmd
scripts/run_analysis_flow_serve.cmd
```

脚本内会设置：

```bat
set PREFECT_API_URL=http://127.0.0.1:4200/api
set GAME_DATA_SOURCE=robotgateway
set ROBOTGATEWAY_BASE_URL=http://127.0.0.1:9000
set ROBOTGATEWAY_CALLBACK_URL=http://127.0.0.1:9000/callbacks/analysis
```

## 4. RobotGateway 向 myAgent 发送消息

RobotGateway 通过 myAgent 的 Webhook 接口发送玩家事件。

### 4.1 接口定义

```http
POST /webhooks/player-event
Host: <myagent-host>:8000
Content-Type: application/json
X-API-Key: <tenant-api-key>
```

完整 URL 示例：

```text
http://127.0.0.1:8000/webhooks/player-event
```

### 4.2 鉴权方式

RobotGateway 必须在请求头中携带：

```http
X-API-Key: <tenant-api-key>
```

myAgent 的认证流程：

```text
X-API-Key
-> Redis auth_cache 查询
-> 未命中则查 PostgreSQL tenants 表
-> 验证 tenant 是否 active
-> 写入 request.state.tenant_id
-> 后续分析使用 tenant_id 做数据隔离
```

缺少或无效 API Key 时，myAgent 返回：

```json
{
  "detail": "缺少X-API-Key"
}
```

或：

```json
{
  "detail": "无效的 API Key"
}
```

### 4.3 请求体通用字段

```json
{
  "user_id": "player_001",
  "event_type": "offline",
  "timestamp": 1779235200.0,
  "snapshot": {}
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `user_id` | string | 是 | 玩家 ID |
| `event_type` | string | 是 | 事件类型：`online` / `offline` / `behavior_checkpoint` |
| `timestamp` | number | 是 | 事件时间戳，Unix 秒 |
| `snapshot` | object | 否 | 玩家快照。`offline` 时建议携带，可减少一次 myAgent 到 RobotGateway 的快照拉取 |
| `session_id` | string | 条件必填 | `behavior_checkpoint` 事件必填 |
| `behavior_event` | object | 否 | 行为事件详情，`behavior_checkpoint` 使用 |

## 5. 事件类型说明

### 5.1 offline：请求 myAgent 分析玩家

RobotGateway 在玩家离线、会话结束或达到需要 AI 分析的检查点时发送。

请求示例：

```http
POST http://127.0.0.1:8000/webhooks/player-event
Content-Type: application/json
X-API-Key: gap_test_alpha_key_002
```

```json
{
  "user_id": "player_001",
  "event_type": "offline",
  "timestamp": 1779235200.0,
  "snapshot": {
    "user_id": "player_001",
    "player_name": "模拟玩家_player_001",
    "level": 28,
    "vip_level": 2,
    "currencies": {
      "gold": 128000,
      "diamond": 860
    },
    "stamina": 72,
    "play_hours": 42.5,
    "main_quest_id": "chapter_learning_03",
    "main_quest_progress": 62,
    "pvp_rating": 1350,
    "game_specific": {
      "source": "robotgateway",
      "current_area": "商业区",
      "target_area": "学习中心",
      "profession": "程序员",
      "recent_activities": ["购物", "学习编程课程", "健身"],
      "bottlenecks": ["学习课程数量偏少", "行动目标不够聚焦"]
    }
  }
}
```

成功调度响应：

```json
{
  "status": "scheduled",
  "user_id": "player_001",
  "flow_run_id": "6c6838df-1b17-4d3b-acc1-f119924c5ab9"
}
```

重复事件被去重响应：

```json
{
  "status": "debounced",
  "user_id": "player_001"
}
```

处理规则：

- myAgent 使用 Redis key `debounce:{user_id}` 做去重。
- 去重窗口由 `OFFLINE_TRIGGER_MINUTES` 控制。
- 如果同一玩家在窗口内重复发送 `offline`，后续请求返回 `debounced`。
- 如果请求携带 `snapshot`，Prefect Flow 直接使用该快照。
- 如果请求不携带 `snapshot`，Prefect Flow 会主动向 RobotGateway 拉取快照。

### 5.2 online：取消或清理待分析状态

RobotGateway 在玩家重新上线时发送。

请求示例：

```json
{
  "user_id": "player_001",
  "event_type": "online",
  "timestamp": 1779235500.0
}
```

响应示例：

```json
{
  "status": "cancelled",
  "user_id": "player_001"
}
```

处理规则：

- myAgent 删除 Redis 去重 key `debounce:{user_id}`。
- 如果 Redis 中记录的是已提交的 Prefect Flow Run ID，myAgent 会尝试取消该 Flow Run。
- 如果 Flow Run 已经完成、失败或 Prefect 客户端取消接口不可用，myAgent 只记录 warning，不影响 online 响应。

### 5.3 behavior_checkpoint：记录在线行为检查点

RobotGateway 在玩家在线期间上报关键行为，用于后续意图推断和长期记忆。

请求示例：

```json
{
  "user_id": "player_001",
  "event_type": "behavior_checkpoint",
  "timestamp": 1779235600.0,
  "session_id": "session_001",
  "behavior_event": {
    "type": "quest_completed",
    "data": {
      "quest_id": "main_03",
      "duration_seconds": 420
    }
  },
  "snapshot": {
    "level": 29,
    "main_quest_progress": 70
  }
}
```

响应示例：

```json
{
  "status": "recorded",
  "user_id": "player_001"
}
```

处理规则：

- `behavior_checkpoint` 必须携带 `session_id`。
- myAgent 写入 `session_events` 表。
- 该事件不会直接触发离线分析。
- 后续 `offline` 分析时，Agent 可读取这些事件辅助判断玩家意图。

## 6. myAgent 向 RobotGateway 拉取快照

当 RobotGateway 发送 `offline` 事件但未携带 `snapshot` 时，myAgent 会主动调用 RobotGateway 的玩家快照接口。

### 6.1 接口定义

RobotGateway 需要提供：

```http
GET /players/{user_id}/snapshot
Host: <robotgateway-host>:9000
X-API-Key: <optional-snapshot-api-key>
```

完整 URL 示例：

```text
http://127.0.0.1:9000/players/player_001/snapshot
```

### 6.2 请求头

如果 myAgent 配置了 `ROBOTGATEWAY_SNAPSHOT_API_KEY`，会发送：

```http
X-API-Key: <ROBOTGATEWAY_SNAPSHOT_API_KEY>
```

如果未配置，则不发送该 header。

### 6.3 响应格式

RobotGateway 可以直接返回 snapshot object：

```json
{
  "user_id": "player_001",
  "player_name": "模拟玩家_player_001",
  "level": 28,
  "pvp_rating": 1350,
  "game_specific": {
    "current_area": "商业区"
  }
}
```

也可以返回带 `snapshot` 包装的 object：

```json
{
  "snapshot": {
    "user_id": "player_001",
    "player_name": "模拟玩家_player_001",
    "level": 28,
    "pvp_rating": 1350,
    "game_specific": {
      "current_area": "商业区"
    }
  }
}
```

myAgent 当前两种格式都能处理。

### 6.4 快照字段建议

快照字段全部使用 JSON 原生类型，建议使用 snake_case 命名。

推荐字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | string | 玩家 ID |
| `player_name` | string | 玩家展示名 |
| `level` | number | 等级或阶段 |
| `vip_level` | number | VIP 或付费等级 |
| `currencies` | object | 货币、资源 |
| `stamina` | number | 体力、能量 |
| `play_hours` | number | 累计游戏时长 |
| `login_days` | number | 累计登录天数 |
| `last_login_at` | number | 最近登录时间戳 |
| `last_offline_at` | number | 最近离线时间戳 |
| `session_count` | number | 会话次数 |
| `online_today_hours` | number | 今日在线时长 |
| `main_quest_id` | string | 当前主线或核心任务 |
| `main_quest_progress` | number | 主线进度 |
| `daily_quest_remaining` | number | 今日剩余日常 |
| `pvp_rating` | number | PVP 评分 |
| `pvp_rank` | number | PVP 排名 |
| `pvp_rating_change` | number | 最近评分变化 |
| `friend_count` | number | 好友数量 |
| `guild_name` | string | 公会名称 |
| `game_specific` | object | 游戏或托管平台自定义字段 |

`game_specific` 中建议放 RobotGateway 更了解的领域状态，例如：

```json
{
  "source": "robotgateway",
  "current_area": "商业区",
  "target_area": "学习中心",
  "profession": "程序员",
  "recent_activities": ["购物", "学习编程课程", "健身"],
  "available_actions": [
    {
      "action_id": "observe_current_state",
      "description": "观察当前状态"
    },
    {
      "action_id": "move_to_location",
      "description": "移动到指定地点"
    }
  ],
  "bottlenecks": ["学习课程数量偏少", "行动目标不够聚焦"]
}
```

### 6.5 快照拉取失败处理

以下情况 myAgent 会认为快照拉取失败：

- RobotGateway 返回非 2xx。
- 响应不是合法 JSON。
- 响应不是 JSON object。
- 响应中既不是有效 snapshot，也没有可用的 `snapshot` 字段。
- 请求超时。

失败后由 Prefect task 重试机制处理。当前 `fetch-snapshot` task 最多重试 2 次，间隔 30 秒。

## 7. myAgent 向 RobotGateway 发送分析完成回调

myAgent 在分析结果写入 PostgreSQL 后，主动 POST 到 RobotGateway。

### 7.1 触发时机

触发顺序：

```text
run_agent_task
-> store_result_task
-> send_callback_task
```

只有 `store_result_task` 成功后，才会进入 callback。

### 7.2 接口定义

RobotGateway 需要提供一个 callback 接收地址。地址由 myAgent 配置：

```env
ROBOTGATEWAY_CALLBACK_URL=http://127.0.0.1:9000/callbacks/analysis
```

myAgent 请求：

```http
POST /callbacks/analysis
Host: <robotgateway-host>:9000
Content-Type: application/json
X-Callback-API-Key: <optional-callback-api-key>
```

完整 URL 示例：

```text
http://127.0.0.1:9000/callbacks/analysis
```

### 7.3 请求头

myAgent 一定发送：

```http
Content-Type: application/json
```

如果配置了 `ROBOTGATEWAY_CALLBACK_API_KEY`，额外发送：

```http
X-Callback-API-Key: <ROBOTGATEWAY_CALLBACK_API_KEY>
```

### 7.4 请求体

```json
{
  "event_type": "analysis.completed",
  "tenant_id": "tenant_001",
  "user_id": "player_001",
  "timestamp": "2026-06-03T01:00:00.000000+00:00",
  "snapshot": {
    "level": 28,
    "pvp_rating": 1350
  },
  "analysis": {
    "player_profile": {
      "playstyle": "explorer",
      "engagement_level": "medium",
      "current_goal": ["探索新区域", "完成主线任务"],
      "bottlenecks": ["等级限制", "装备不足"]
    },
    "recommended_actions": [
      {
        "action_type": "observe_current_state",
        "priority": "high",
        "reason": "先确认当前状态，避免在缺少上下文时执行高风险动作",
        "payload": {}
      }
    ]
  }
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `event_type` | string | 固定为 `analysis.completed` |
| `tenant_id` | string | myAgent 解析到的租户 ID |
| `user_id` | string | 玩家 ID |
| `timestamp` | string | ISO 8601 UTC 时间 |
| `snapshot` | object | 本次分析使用的玩家快照 |
| `analysis` | object | myAgent 生成的分析结果 |

### 7.5 推荐动作结构

当前 `recommended_actions` 中的动作结构来自 myAgent 的 `RecommendedAction` 模型：

```json
{
  "action_type": "observe_current_state",
  "priority": "high",
  "reason": "推荐原因",
  "payload": {},
  "goal_metric": null,
  "goal_value": null,
  "expected_hours": null
}
```

当前基础动作类型包括：

| action_type | 说明 |
|---|---|
| `observe_current_state` | 观察当前状态 |
| `move_to_location` | 移动到指定地点 |
| `stop_moving` | 停止移动 |
| `jump` | 跳跃 |
| `play_basic_action` | 执行基础动作 |

`payload` 建议：

| action_type | payload 建议 |
|---|---|
| `observe_current_state` | 可为空 |
| `move_to_location` | `location_id` 或 `position` |
| `stop_moving` | 可为空 |
| `jump` | `count` |
| `play_basic_action` | `action_id` |

追踪字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `goal_metric` | string/null | 可量化完成指标，对应 snapshot 字段名 |
| `goal_value` | number/null | 目标值 |
| `expected_hours` | number/null | 预计完成小时数，用于计算截止时间 |

RobotGateway 不应直接无条件执行 `recommended_actions`。建议先做：

```text
动作白名单校验
-> 玩家当前状态复核
-> 安全校验
-> 节奏控制
-> 最终执行或人工审核
```

### 7.6 RobotGateway 响应要求

RobotGateway 收到 callback 后，只要成功接收并持久化或入队，建议返回任意 2xx。

示例：

```json
{
  "status": "received",
  "user_id": "player_001"
}
```

myAgent 只检查 HTTP 状态码：

- 2xx：视为成功。
- 非 2xx：视为失败，抛出 callback error。
- 网络异常或超时：视为失败。

当前 `send-robotgateway-callback` task 最多重试 2 次，间隔 30 秒。

## 8. 错误码与异常处理

### 8.1 RobotGateway 调 myAgent 的常见返回

| 状态码 | 场景 | 返回示例 |
|---:|---|---|
| 200 | 调度成功 | `{"status":"scheduled","user_id":"player_001","flow_run_id":"..."}` |
| 200 | 去重命中 | `{"status":"debounced","user_id":"player_001"}` |
| 200 | online 取消 | `{"status":"cancelled","user_id":"player_001"}` |
| 200 | 行为检查点记录 | `{"status":"recorded","user_id":"player_001"}` |
| 400 | 未知事件类型 | `{"detail":"未知事件类型: xxx"}` |
| 401 | 缺少或无效 API Key | `{"detail":"缺少X-API-Key"}` 或 `{"detail":"无效的 API Key"}` |
| 422 | 请求体缺少必填字段 | FastAPI validation error |
| 422 | behavior_checkpoint 缺少 session_id | `{"detail":"behavior_checkpoint 事件必须提供 session_id"}` |
| 429 | 限流 | `{"detail":"请求过于频繁，请稍后再试"}` |

### 8.2 myAgent 调 RobotGateway 的失败处理

| 链路 | 失败场景 | myAgent 行为 |
|---|---|---|
| 拉取 snapshot | 非 2xx / 超时 / JSON 无效 | 抛出 `DatabaseError`，Prefect task 重试 |
| 发送 callback | `ROBOTGATEWAY_CALLBACK_URL` 未配置 | 跳过，不视为失败 |
| 发送 callback | 非 2xx / 超时 / 网络异常 | 抛出 `RobotGatewayCallbackError`，Prefect task 重试 |

## 9. 幂等性与去重

### 9.1 offline 事件去重

myAgent 使用 Redis key：

```text
debounce:{user_id}
```

流程：

```text
收到 offline
-> SET debounce:{user_id} pending-xxx EX <ttl> NX
-> SET 成功：提交 Prefect Flow Run
-> SET 失败：返回 debounced
-> Flow Run 创建成功后，将 key 更新为 flow_run_id
```

TTL 来源：

```env
OFFLINE_TRIGGER_MINUTES=5
```

### 9.2 callback 幂等建议

myAgent callback 当前没有额外生成业务幂等 ID。RobotGateway 建议以以下组合作为幂等判断依据：

```text
event_type + tenant_id + user_id + timestamp
```

如果 RobotGateway 需要更强幂等性，建议后续在 callback payload 中增加：

```json
{
  "analysis_id": "uuid",
  "flow_run_id": "uuid"
}
```

当前代码尚未在 callback payload 中包含这两个字段。

## 12. 常见问题

### 12.1 offline 返回 debounced 是不是失败

不是。`debounced` 表示同一玩家在去重窗口内已经有分析任务或刚提交过分析任务。RobotGateway 可以认为这次事件已被 myAgent 接收，但没有创建新的分析任务。

### 12.2 callback 没收到怎么办

按顺序检查：

1. `ROBOTGATEWAY_CALLBACK_URL` 是否配置。
2. Prefect Flow 是否执行到 `store_result_task` 之后。
3. `send-robotgateway-callback` task 是否失败。
4. RobotGateway callback endpoint 是否返回 2xx。
5. RobotGateway 是否因为鉴权拒绝了 `X-Callback-API-Key`。
6. myAgent 的 LLM/RAG 是否在前置节点失败，导致没有进入 callback。

### 12.3 myAgent 为什么还会调用 RobotGateway snapshot 接口

如果 RobotGateway 在 `offline` Webhook 中没有传 `snapshot`，myAgent 需要通过 `GET /players/{user_id}/snapshot` 获取玩家当前状态。推荐 RobotGateway 直接在 `offline` 请求中携带 snapshot，这样链路更短，也更容易排查。

### 12.4 RobotGateway 是否应该查询 myAgent 的 latest/history 接口

不建议作为主链路。`GET /api/v1/analysis/{user_id}/latest` 和 `GET /api/v1/analysis/{user_id}/history` 更适合作为内部查询、调试或后台管理接口。RobotGateway 获取分析结果的主方式应是接收 myAgent callback。

### 12.5 分析任务长时间不完成怎么办

常见原因：

- Prefect worker 未启动。
- `PREFECT_API_URL` 指向错误。
- `analysis_flow/offline-analysis` deployment 未注册。
- LLM API Key、Base URL 或模型配置错误。
- Embedding/RAG 服务不可用。
- RobotGateway snapshot 接口不可访问。
- 数据库或 Redis 不可用。

## 14. 验收标准

双方联调完成时，至少应满足：

- RobotGateway 能成功请求 `GET /health` 确认 myAgent 在线。
- RobotGateway 能成功 `POST /webhooks/player-event` 发送 `offline`。
- myAgent 能返回 `scheduled` 或明确的 `debounced`。
- 如果 `offline` 不带 snapshot，myAgent 能成功调用 RobotGateway `GET /players/{user_id}/snapshot`。
- myAgent 能完成 Prefect 分析流程并写入分析结果。
- myAgent 能向 RobotGateway callback URL 发送 `analysis.completed`。
- RobotGateway 能返回 2xx，并能记录 callback payload。
- RobotGateway 不直接无校验执行推荐动作，而是经过安全校验后再执行。
