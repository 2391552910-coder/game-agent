**AI 分析耗时偏长的详细分析**

这次完整流程耗时：

```text
总流程：219.045 秒，约 3 分 39 秒
run-agent：218.908 秒，约 3 分 39 秒
fetch snapshot：0.033 秒
store result：0.015 秒
callback：0.030 秒
```

所以瓶颈几乎全部在 `run-agent`。

按当前执行链路，`run-agent` 内部大致是：

```text
fetch_snapshot
-> retrieve_rag_context
-> intent_inference
-> goal_evaluation
-> gather_context
-> behavior_analysis
-> action_reasoning
-> merge_output
-> tracking_update
-> memory_update
```

主要耗时来源有几个：

1. **LightRAG 初始化和首次查询很重**

首次 `get_rag()` 会初始化 Redis、Milvus、Neo4j、EmbeddingFunc、collection 检查、Neo4j index 检查等。日志里能看到：

```text
Initialized Redis KV storage
Milvus collection initialized
Connected to neo4j
Embedding workers initialized
```

这部分会把首次分析显著拉长。

2. **RAG 查询次数多**

本次不是只查一次 RAG。至少包括：

- `retrieve_rag_context_node` 的主图 RAG 查询
- `gather_context_node` 中工具触发的多次 `dynamic_rag_query`
- 每次 RAG 查询内部又会做 keyword extraction、local/global graph search、vector search、chunk merge、rerank

日志里出现了多轮：

```text
Query nodes...
Query edges...
Local query...
Global query...
Final context...
```

这说明每次动态查询都走了一整套 LightRAG 检索流程。

3. **rerank 403 触发重试，浪费时间**

日志里反复出现：

```text
Rerank API error 403: AllocationQuota.FreeTierOnly
Error during reranking: RetryError..., using original chunks
```

LightRAG 最后会回退使用原 chunks，所以结果能出来，但每次 rerank 失败前都有网络请求和重试。由于本次有多次 RAG 查询，这个损耗会被放大。

这是当前最容易优化的一项。

4. **LLM 调用是串行的**

目前图是线性边：

```text
intent_inference -> goal_evaluation -> gather_context -> behavior_analysis -> action_reasoning
```

每个节点都要等上一个节点完成。并且 `gather_context` 内部最多 3 轮 LLM + 工具调用，工具里又可能触发 RAG。

即使 `LIGHTRAG_LLM_MAX_ASYNC=2`，主图节点本身仍然是串行的。

5. **`.env` 里 fast/default 都是 gpt-5.5**

当前 `.env` 中：

```env
OPENAI_DEFAULT_MODEL=gpt-5.5
OPENAI_FAST_MODEL=gpt-5.5
```

这意味着“快速模型”节点实际上也在用同一个较重模型。`intent_inference`、`behavior_analysis`、`gather_context` 这类节点如果能用更快模型，整体会明显下降。

6. **知识库缺少关键规则，导致 Agent 更保守，也可能引发额外查询**

最终结果里 AI 明确说：学习中心坐标和进入规则缺失。

这会导致 Agent 不能直接生成确定动作，只能继续查规则或降级成观察/已知地点移动。规则越完整，动态 RAG 反复查证的概率越低。

建议优化顺序：

1. 先修 rerank：额度恢复，或临时加配置禁用 rerank。
2. 给 `OPENAI_FAST_MODEL` 配一个更快模型，不要和 default 都用 gpt-5.5。
3. 给每个 LangGraph 节点加耗时日志，精确拆分每个节点耗时。
4. 在 API / Prefect serve 启动时预热 `get_rag()`，避免首次请求承担初始化成本。
5. 控制 `gather_context` 的动态 RAG 查询次数，避免相近问题重复检索。
6. 补齐游戏知识库里的地点、坐标、进入规则和基础动作规则。
